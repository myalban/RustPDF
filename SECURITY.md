# Security policy

## Reporting a vulnerability
Please **do not open a public issue** for a security problem. Use GitHub's private reporting instead:
**Security → Report a vulnerability** on the repository page. I will answer as soon as I can and credit you in the fix unless you prefer otherwise.

Useful details: the RustPDF version, your OS, and a PDF (or steps) that reproduces the problem.

## Opening a PDF you do not trust
A PDF is a complex file format and every PDF reader, including this one, has had or will have parsing bugs.
RustPDF parses documents with **PDFium** (the engine of Chrome, written in C++) and with **lopdf** (Rust).

**Protected view (default).** Every document first opens in a *protected view*: a separate worker process (`rustpdf --pdf-worker`)
parses and renders it with PDFium and sends back only bitmaps and link targets. The worker receives the file over a pipe, never
touches the file system, and the application validates everything it sends back (sizes, bitmap length, numbers, link addresses).
A worker that stops responding for 40 seconds is killed. Per operating system:
- **Windows**: the worker runs in an *AppContainer* (no access to your files, no network, no other programs) inside a job object
  (one process, 3 GiB memory cap, no UI access) with process mitigations (no dynamic code, strict handle checks, no remote or
  low-integrity images). Its copy of the program is staged in `%LOCALAPPDATA%\RustPDF\worker`; the AppContainer profile is named `RustPDF.ProtectedViewer`.
- **Linux**: the worker locks itself with `no_new_privs`, Landlock (no file writes, no TCP on kernel 6.7+) and a seccomp filter
  (no sockets, no new programs, no `ptrace`, `mount`, `bpf`…). It can still *read* files your user can read, by design of this filter.
- **macOS**: the worker enters the Seatbelt `pure-computation` profile. This path has **not been tested on real hardware yet**.

You can check the isolation on your machine with `rustpdf --sandbox-check [file.pdf] --selftest`: it tries to read a file,
write a file, start a program and reach the network from inside the worker, and reports each as *blocked* or *ALLOWED*.

**Limits, stated plainly.** *Enable editing* opens the document in the editor, which parses it with PDFium **inside the
application process, without a sandbox**: only do that for files you trust. A bug in the operating system's isolation itself,
or a PDFium bug chained with a kernel bug, is not covered. For documents that are really hostile, a virtual machine or
Windows Sandbox remains the safest choice.

What RustPDF does to reduce the risk:
- **PDF JavaScript is never executed** (PDFium is used without a JavaScript engine), and PDF actions such as *Launch* are not implemented.
- **Links** inside a PDF are opened only if they are `http`, `https` or `mailto`, and without going through a shell. `file:`, `javascript:`, network shares and anything else are refused.
- **Attachments** are only saved where you tell them to be saved, never opened or run.
- **Library loading**: PDFium is loaded only from the application folder (never from the folder of the document being opened), and on Windows the process restricts DLL searching to the application folder and System32, disables extension points and refuses images from low-integrity locations. This blocks "DLL planting" next to a downloaded PDF.
- **Downloads are verified**: the PDFium archive fetched by the build scripts is checked against a pinned SHA-256. A weekly job tells the maintainer when a newer PDFium build (with its security fixes) is available.
- **Resource limits**: files over 1 GiB are refused, rendered bitmaps are capped, and images you import are decoded with size limits.
- **Password-protected documents stay protected**: PDFium keeps the encryption when it saves, and when an edit made through `lopdf` would have decrypted a document that has no user password, the original permissions are written back on save (tested). Recovery copies are written with the same protection and, on Linux and macOS, readable by their owner only.
- **Private keys**: a self-signed certificate generated by RustPDF requires a password; the backup copy kept in the data folder is a password-protected PKCS#12 file with a sanitized name and owner-only permissions.
- **Update check**: HTTPS only (redirects included), a 1 MB maximum answer, and the address can never be interpreted as a command-line option.
- **Dependencies** are checked weekly against the RustSec advisory database, and updates are proposed automatically.

## What else to know
- No document content is sent anywhere. The only network access is an optional once-a-day request to GitHub to look for a newer release (Preferences → *Check for updates*); nothing is downloaded or installed automatically.
- Documents with unsaved changes are copied to the application data folder for crash recovery (`%APPDATA%\RustPDF\autosave`, `~/.config/rustpdf/autosave`, `~/Library/Application Support/RustPDF/autosave`) and removed once the document is saved or the recovery is dismissed. The copies are not encrypted; disable autosave in Preferences if the documents are sensitive.
- Digital signatures use the RustCrypto `rsa` crate, which has a known timing side channel (RUSTSEC-2023-0071, no fix available yet) that matters for servers, not for a desktop app signing locally with its own key. They do not validate the certificate chain against a trust store: a valid mark means "unmodified since signed by this key", not "signed by a trusted identity".
- Redaction removes the text, the image pixels and the annotations under the marked area. Always re-open the saved file and check before sharing it.
- Release binaries are not code-signed yet, so Windows SmartScreen and macOS Gatekeeper warn on first launch.

## Verifying a download
Each release includes `SHA256SUMS.txt`. After downloading, compare the hash of your file:
```
sha256sum RustPDF-portable.zip            # Linux / macOS: shasum -a 256 <file>
Get-FileHash .\RustPDF-portable.zip       # Windows PowerShell
```
The workflows that build the releases pin every GitHub Action to a commit hash, run with read-only permissions, and only the publishing step may write.

## Known limitation
Structural edits (insert, delete, rotate pages, annotations…) work through `lopdf`, which cannot open a document that has a *user* password; RustPDF then reports an error. Remove the password protection first, edit, then protect it again (Document → Security).
